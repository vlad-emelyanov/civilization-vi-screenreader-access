# Xbox controller support (design, 2026-10-27)

Goal: a blind player can play with an Xbox controller instead of the keyboard. The controller has far fewer buttons than the keyboard, so buttons are multipurpose, depending on what has the focus. This file is the design and the contract between the console app, the Lua side and the tests. Current state at the end.

## How controller input reaches the mod

Civ VI on PC does not react to a gamepad (the engine carries console-port leftovers: `Keys.PAD_*`, `GestureType="Controller"` rows in `InputConfiguration.xml`, `UIManager:IsGamepadActive`; none of it is verified to do anything on PC, and we cannot depend on it). The mod only sees keys, so:

- The **console app** (`ScreenreaderAccess.Console`, which must run anyway for speech) polls the controller through XInput and **injects keyboard keys** into the game window (`SendInput` with scan codes, exactly like `util/civctl.ps1` `Chord`). Buttons that mean the same thing as a keyboard key everywhere (A = Enter, B = Escape, Y = Space, left stick = arrows, D-pad = Home/End/Tab) are sent as that key; lists and screens with sections translate Home/End/Tab for the pad (below, "In lists"). Buttons without a keyboard equivalent are sent as keys the game and the mod do not use (F13 to F24, with Control for a second bank) and are interpreted by the mod.
- The console app only injects while the game window is in the foreground, and only when a controller is connected. `--no-gamepad` turns the feature off.
- **Controller mode** is a flag in the mod: on when the controller is in use, off when the keyboard is. The console app sends `F22` (mode on) before the first controller input after keyboard use and `F23` (mode off) when a physical key is pressed after controller use (a low-level keyboard hook; injected keys do not count). In controller mode a few keys change meaning on the bare map (below); outside it the keyboard behaves as before. The first physical key after controller use may be swallowed on the bare map (it arrives before F23); that is accepted.
- **Tests do not need a controller**: `civctl key F15` is exactly what the console app sends for RB. Regress scripts drive the controller layer with the F-keys (comment the button name in the script).
- Steam Input must be disabled for the game (Steam library, Civilization VI, Properties, Controller: "Disable Steam Input"), otherwise Steam also translates the controller into keyboard and mouse and every press arrives twice.

Popups and the in-game menu sit above the hub and take every key: there A/B/Y/sticks work through their keyboard equivalents and the F-keys do nothing. Game screens (tech tree, city-states ...) get keys after the hub: the hub passes every mode-dependent button through while `HubCore.IsGamePopupOpen()`, LB/RB too: they are the screen's own sections (only when EVERY open screen is in `HubGamepad`'s `BUMPER_SCREENS` list, by context id; the diplomacy and deal views also have the `LeaderScene` context open beside them, so it is listed too: `KeyNavList` screens say "No tabs here" without tabs; any other open screen keeps "Close the screen first", never silent; Menu likewise). The research and civics choosers are side panels (`/InGame/TopLevelHUD`), not game screens: while one is open and no hub list is, LB/RB pass to its `KeyNavList` ("No tabs here"; PageUp/PageDown are its groups, "No groups in this list") instead of the ring (`HubGamepad.IsChooserOpen`). The great works overview's Tab (hence LB/RB) is a real section key: first slot of the next / previous building. The front end (main menu, setup) has no hub: A, B, Y, sticks and D-pad work through their key equivalents, the other buttons do nothing.

Right stick and stick clicks (selection changes) work on the bare map and inside hub lists (a selection change closes the list, as it does with the keyboard); they pass through while a game screen is open.

Keyboard only: the 5-tile cursor jumps (`KeyNavJumpCell*`, Control+Shift+Arrows) have no pad button (the right stick is taken by selection changes); on the pad use the places list (Foreign lands category) to reach far tiles.

## In lists: D-pad, bumpers, group jump

`Gamepad.TranslateListKey( key, isControl, active )` (pure, unit-tested) maps the pad's keys to the keys a list already knows, only in controller mode and without Shift/Alt: Home/End to Up/Down, Tab/Control+Tab to Right/Left, F14/F15 (LB/RB) to Control+Tab/Tab; it also says whether the key came from a bumper. `KeyNavList.HandleInput` applies it first; screens with their own Tab/Home/End handling call `Gamepad.WrapInput( input )` (an input proxy with the translated key) at the top of the handler: tech/civics tree (`TreeNav`), deal view, reports, trade overview, great works, espionage overview, world rankings, climate, civilopedia. Not covered (they keep Home/End/Tab as they were, the D-pad still sends them): Options, save game menu, religion screen's hand-written parts, world congress, map search, advisor popup, expansion intro and the front end screens without `KeyNavList`.

PageUp/PageDown in controller mode never reach the game as input actions (Gathering Storm binds PageDown to the Climate screen): WorldInput's catcher swallows them on the bare map, `HubGamepad` while a screen outside its `PAGE_SCREENS` list is open (the Climate screen included); the keyboard's keep working. Key names: the game's own Lua never uses a page key; `Gamepad.PageKey` expects `Keys.VK_PRIOR` / `Keys.VK_NEXT` (engine names are Win32-like) with fallbacks, and the console app injects them with the extended-key flag like the arrows.

Controller mode in a context without the hub (game screens, popups, the front end): `Gamepad.Follow()` (called by `KeyNavList_Create` and `WrapInput`) listens to `LuaEvents.SRA_GamepadMode` (the hub broadcasts it) and asks once with `LuaEvents.SRA_GamepadModeRequest()`; `Gamepad.NoteModeKey` lets a list that sees F22/F23 itself (a popup above the hub, the front end) set the mode and broadcast it with `SRA_GamepadMode` on a change (listeners only store, so no loop); `KeyNavList.Open` asks again with `SRA_GamepadModeRequest`.

PageUp/PageDown (a keyboard key too) in a `KeyNavList` jump to the first item of the previous/next group (`KeyNavList_GroupTarget`, pure, wraps) and speak it with the group name (`sectionCounts = true` adds the item count: "Builder, 3: ..."); a list without groups says "No groups in this list", one group "Only one group in this list". The keys are always consumed, so PageDown does not open the Climate screen underneath. Lists with groups: the production panel (districts and buildings / wonders / units / projects), Places "Your units" (by unit type; the list opens on the selected unit when there is one). The console app sends PageUp/PageDown instead of Up/Down/Home/End while LB or RB is held (left stick and D-pad, same repeat, no Shift) and then suppresses that bumper's KeyUp, like a held RT used as Shift (`HubGamepad`'s taint logic needs no change: a Page key counts as another key).

## The ring (LB / RB)

The in-game UI is a ring of keyboard lists; RB opens the next, LB the previous; B closes the open one back to the map. Order:

1. Notifications (Control+N list)
2. Top panel (Control+Y list)
3. Lenses (new, `HubLenses.lua`): one item per lens the number keys toggle ("Appeal lens, off"); A toggles it (the same speech as the number key) and the list stays open with the item refreshed; Y reads the legend
4. Diplomacy (V list of met civilizations)
5. Screens (new, `HubScreens.lua`): the launch bar and partial-screen hooks: Tech tree, Civics tree, Government, Religion, Great People, Great Works, Governors, City-States, Espionage, Trade routes, World rankings, Climate, Era progress, Reports, Civilopedia. A closes the list and opens the screen through the same function the game's button runs (`LuaEvents.SRA_OpenScreen(name)` handled by our `LaunchBar.lua` / `PartialScreenHooks.lua` overrides); the screen announces itself as it does today; B closes it. An item whose hook is hidden says "not available"
6. Places (J list)

RB from the bare map opens 1, LB opens 6; from a ring list they move; from another hub list (unit actions, settle browser, city report ...) RB opens 1 and LB 6. `HubPad.RingStep(currentModeName, +1|-1)` is a pure function (unit-tested).

A hub list with sections takes LB/RB first (`HubGamepad`, `HubPad.BumperAction( modeName, hasTabs, atEdge )`, pure): Places (J) is a ring list with sections, its categories are sub-stops of the ring: RB on the last category continues to the next ring list (Notifications), LB on the first category to the previous one (Screens); the help list is outside the ring, its sections just wrap. A list declares its edge with `tabEdge = function( step )` (the facade forwards `HasTabs` / `AtTabEdge`). Known asymmetry: LB from Notifications opens Places on its first category, not its last.

## The wheel (experiment, 2026-10-29)

A GTA-style weapon wheel for the short lists of the main interface: the ring's Top panel, Lenses, Diplomacy and Screens lists (`wheel = true` in their `KeyNavList_Create`; Notifications and Places are long or sectioned and have none yet). Hold LT, point the left stick, the list's entries sit around the stick like a clock face (item 1 straight up, clockwise; 4 items = up, right, down, left; 8 = the compass). Each change of direction jumps to that item and speaks it as a normal move ("Government, 3 of 15"); the same item is not spoken twice. Releasing LT leaves the focus there (pointing never activates: A chooses). A list longer than 24 items gets a coarse jump (every N/24-th item), the stick then moves one by one.

- **Console app** (`GamepadMapper.WheelSlot`, pure, unit-tested): while LT is held the left stick sends no arrows; its angle (deadzone ~73 %, so a stick springing back keeps the slot; 4 degrees of hysteresis at the slot borders) picks one of 24 slots of 15 degrees, clockwise from up, sent as one tap per slot change: slots 0..11 = Shift+F13..F24, 12..23 = Control+Shift+F13..F24 (`GamepadMap.WheelKey`). LT's F16 KeyUp is suppressed when the wheel was used (like RT as Shift), and after the wheel the left stick stays silent until it is centred once (releasing LT while pointing must not also move the focus).
- **Lua**: `Gamepad.WheelOf( key, isControl, isShift )` (slot or nil) and `Gamepad.WheelIndex( slot, count )` (pure: `floor( slot * count / 24 + 0.5 ) % count + 1`). With Shift the F-keys are never buttons: `Gamepad.ButtonOf` / `NoteModeKey` take `isShift` and return nil (Shift+F22 is slot 9, not ModeOn), every caller passes it; Options ignores wheel keys. `KeyNavList.HandleInput` handles them first (KeyDown jumps, both consumed); a list without `wheel = true` consumes them and says "No wheel in this list" once per sweep; `HubGamepad` passes them to an open hub list, chooser or game screen and says "No list to point at" on the bare map (once until another key).
- Not covered: every other list and screen (screens without `KeyNavList` ignore the wheel keys silently). Unverified with a real pad: the feel of the deadzone, hysteresis and 24 slots, (the modifier delays are gone with posted keys); verified in game with `civctl key Shift+F19` etc. (Top panel, Lenses, Diplomacy, Screens; Places refuses).

## X in lists

Each list names its X action (the key the list already has for it): notifications: dismiss (Delete); places: send a unit there (M); every other list: nothing yet. (X is not a section or group key: those are the bumpers.) A list declares it with `extraKeys[ Gamepad.Key( "X" ) ]` (so keyboard users are unaffected) and its help entry mentions "X".

## Controller mode on the bare map: the catcher

Keys that no screen wanted reach `WorldInput` last (it is below the hub and every screen; the game's own Escape-to-menu sits even lower, in `InGame.lua`). In controller mode its default key handlers catch: arrows (cursor move, KeyDown so a held stick repeats), Escape (swallowed), Space (Y), Home / End / Tab-with-Control (D-pad). The decision is the pure function `Gamepad_CatchKey( msg, key, isControl, active )` in `Gamepad.lua` (unit-tested); `WorldInput.lua` calls it from `DefaultKeyDownHandler` / `DefaultKeyUpHandler` and fires `LuaEvents.SRA_PadCursor( dx, dy )`, `SRA_PadDetails()`, `SRA_PadInfo( "next" | "where" | "overview" )`; the hub listens. A key the catcher consumes never becomes an input action (so Home does not also open the in-game menu). The hub keeps controller mode (`Gamepad.SetActive`) and broadcasts it with `LuaEvents.SRA_GamepadMode( active )`; WorldInput keeps a copy. Every F-key button also turns the mode on.

## Help

`HelpText.lua` gets a "Controller" section (the table above in words, one entry per button). In controller mode `HubHelp` lists that section first. Per-list help entries that have an X action mention it.

## Console app

`ScreenreaderAccess.Console/Gamepad/`: `XInputReader` (P/Invoke `xinput1_4.dll` `XInputGetState`, first connected pad of 0..3, disconnected slots re-checked every 2 s), `GamepadMapper` (pure: previous and current state plus time to key events; buttons send KeyDown on press and KeyUp on release; stick directions and the D-pad are digital at 50 % deflection with keyboard-like repeat: left stick and D-pad 350 ms then every 110 ms, right stick 500 ms then every 350 ms; triggers are buttons above 50 %), `KeyInjector` (default: `WM_KEYDOWN` / `WM_KEYUP` posted to the foreground game window, no delays: posted keys bypass the low-level keyboard hooks, so JAWS does not speak "Shift F13" for every pad press, and the game reads the posted Shift / Control messages in order, verified in game for the wheel keys, arrows, the right stick's Control+F-keys, View and B; `--gamepad-sendinput` restores SendInput with scan codes, the extended flag for arrows/Home/End, modifiers held 40 ms around the key and `dwExtraInfo` marking our own events), `ForegroundGuard` (inject only when the foreground window belongs to a `CivilizationVI*` process), `InputDeviceTracker` (WH_KEYBOARD_LL hook: a non-injected key switches to keyboard mode and sends F23; the next controller input sends F22 first). Polling at ~60 Hz on a background thread; console lines "Gamepad: connected (slot 0)", "Gamepad: disconnected", and with `--gamepad-log` every mapped key. `--no-gamepad` disables it. No controller present: the feature idles and says so once.

## Spoken key hints

Spoken text that names a key ("Tab for its actions", "Escape to cancel") must name the controller button when the player uses the pad. The mod marks the key with `SRKey( keyboard[, button] )` (`Accessibility/ScreenReader.lua`), which returns the token `[KEY:keyboard]` or `[KEY:keyboard|button]`. `OutputMessageToScreenReader` passes it through; the console app expands it at speech time (`KeyHints.Expand( text, pad )` in `AccessibleOutputHandler.OutputMessage`), because only it knows the device (a second token, `SRPadHint( text )` = `[PAD:text]`, is spoken as `text` only when the pad is current and removed otherwise; `text` must not contain `]`; the harness `Expand-KeyHints` and the luatest `Spoken()` drop it, `SpokenRaw()` keeps it; `KeyNavList` uses it for ", Y for details" on open; the mirror `SRKbHint( text )` = `[KB:text]` is spoken only when the pad is NOT current, for a hint that names a keyboard-only key, e.g. the unit actions menu's ", key D"; civctl and `Spoken()` keep its text): `Gamepad/InputDevice.PadIsCurrent` is set true when the pad makes the app inject keys and false on a physical key (the same events that send the mode keys F22 / F23; always false with `--no-gamepad` or no pad; `--gamepad-log` prints each switch).

- Keyboard: `keyboard`. Pad: `button` if given (a `Gamepad.Map` name such as X, LB, RSClick is spoken in words, "left bumper", "right stick click" ...; any other text is spoken verbatim), else the default button of the keyboard key, else `keyboard`.
- Defaults (keyboard text compared case-insensitively, mirroring `GamepadMap`; on the bare map Tab is the unit actions menu = D-pad right, so a hint that means "next section" in a list or screen passes the button explicitly: `SRKey( "Tab", "RB" )`, `SRKey( "Control+Tab", "LB" )`; done for the end game menu, the government screen and the deal view): Enter = A, Escape = B, Space = Y, Tab = D-pad right, Control+Tab = D-pad left, Home = D-pad up, End = D-pad down, Up / Down / Left / Right = left stick up / down / left / right, Arrows or "arrow keys" = left stick, "Up and Down" / "Up/Down" and "Left and Right" / "Left/Right" = left stick up and down / left and right, `Shift+<Enter|Home|End|arrow>` = "right trigger plus <that key's button>", F13..F21 = X, left bumper, right bumper, left trigger, right trigger, View button, Menu button, left stick click, right stick click. A malformed or unclosed token is left as is.
- `util/civctl.ps1` (`Expand-KeyHints`) and the Lua test stubs (`Spoken()`; `SpokenRaw()` is unexpanded) always show the keyboard wording, so regress expects do not change.

## Status

The Lua layer, the console app (XInput reader, key injector, mode tracking, held-RT-as-Shift) and the spoken key hints are implemented and verified in game by keyboard: the pad regress scripts (`pad-map`, `pad-select`, `pad-ring`, `pad-screens`, `pad-screens-keys`, `pad-unit-flow`, `pad-x-browse`, `deal-flow`) send the F-keys exactly as the console app does, and `Gamepad.lua`, `GamepadMap.cs` and `util/keybindings.py` are checked against each other. The ring lists, the screens list, the X/LT/RT aliases of the mod's screens and the pad-friendly hints (browsers as first Tab-menu entries, pad-only `, Y for details`, `SRKbHint`) were fixed after the owner's manual pad play.

Added 2026-10-29 (owner request, blind-written scripts `pad-list-dpad`, `pad-bumper-sections`, `list-group-jump`; unit-tested in Lua and C#): the D-pad moves one item in lists, LB/RB are the sections of lists and screens, a held bumper plus up/down jumps groups. Unverified in game: the engine key names for PageUp/PageDown (`Gamepad.PageKey` tries VK_PRIOR/VK_NEXT and alternatives), the hold-bumper rule on a real pad.

What needs a real pad: the held-RT-as-Shift rule (civctl holds one chord, so Shift+Right while F17 is held is untested), the console app's RT-as-Shift, and the aliases of the screens that only have unit tests (government, religion, trade, great works, rankings, civilopedia, options). Whether the engine reacts to a pad on its own is unprobed (Steam Input must be off). Open items: `docs/backlog.md`.
